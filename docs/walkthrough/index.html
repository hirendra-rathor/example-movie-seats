The request

Recorded prompt · unchanged from the build guide

I’d like to build a small movie booking service called Movie Seats.
Let’s start with one screening configured with twelve seats, A1 through A4,
B1 through B4, and C1 through C4. A booking client should be able to ask
which seats are available and request a hold on one or more of them.
I’d like to use Python and FastAPI for a JSON API I can call from a terminal,
with a local SQLite database for reservations.

People booking together need their complete selection. Two clients might ask
for overlapping seats at the same time, and a caller should get either
every seat it requested or no seats at all. When a hold succeeds, I’d like
the service to return a reservation ID the caller can use to look up the
reservation, even after the service restarts.

Give me a design proposal [use $ca-design-proposal].

The design proposal

Recorded assistant response

A booking client needs to hold an entire party’s seat selection and recover the accepted reservation after a restart so that the group is never split by partial allocation.

Milestone 1 — comparison baseline. The approved starter 81dfa9f serves a page and /health; its two smoke tests pass. There is no screening, reservation, or database. This proposal introduces those responsibilities from that source baseline. The overview connects the group’s intentions to allocation rules, responsible components, exchanges, durable facts, and distinguishing checks.

Domain — Intentions, Required capabilities, and Rules. A caller can inspect one screening containing A1–A4, B1–B4, and C1–C4, request one or more seats, and recover the accepted group by its reservation ID. Availability is a snapshot: another caller can win before a later request. The service accepts every requested seat or none. A3 already held means an A2+A3 request leaves A2 available. Independent callers competing for B1 cannot both succeed.

Selection spelling is exact and case-sensitive. An empty group, duplicate seat, unknown identifier, nonstring, or extra request field is invalid; the service will reject mistakes rather than silently deduplicate or reinterpret them. Sorting valid seats makes representation stable without changing selection meaning. These are proposed interface choices within the prompt’s scope. Holds have no completion or expiry behavior at this checkpoint.

Architecture — System context and Runtime units. A terminal client calls a FastAPI service served by Uvicorn. A reservation service owns the allocation decision; the local SQLite engine supplies transaction isolation and durable storage. Every operation opens and closes its own connection. Writers sharing a file coordinate through SQLite, including workers in different processes. This design assumes one host and a local filesystem; it does not establish multi-host database safety.

Subsystem Design — Components. The package is movie_seats.

Package or moduleComponents: existing → proposed responsibility
app.py — changedStarter assembly → initialize the configured store during startup and register booking routes; retain page and health.
domain.py — newNo selection policy → validate exact seat IDs, preserve group meaning, and define caller-visible domain failures.
db.py — newNo persistence → initialize schema version 1, allocate atomically, read consistent snapshots, and recover holds by ID.
api.py — newNo booking boundary → parse JSON, call the store, and translate domain failures into stable HTTP responses.
scripts/acceptance.py — newNo process rehearsal → exercise actual HTTP requests across independent Uvicorn processes and restarts.

Subsystem Interfaces — Interfaces and Exchanges. GET /screening returns the twelve seats with available or held status. POST /reservations accepts {"seats":["A3","A4"]} and returns HTTP 201 with id, canonical seats, and status: "held", after commit. GET /reservations/{id} returns that reservation or 404. Invalid requests return 422, occupied selections 409, and a bounded database lock timeout 503 with Retry-After: 1. The page and exact /health response remain compatible.

A lost creation response remains ambiguous if the caller never learned the ID. Repeating an unkeyed request is not yet safe recovery; milestone 2 supplies that capability. A successful availability read is also not a reservation promise.

State Management — State elements and transaction boundary. Four tables separate the fixed screening inventory, reservation identity/state, immutable requested selection, and current seat claims. A claim’s seat primary key enforces one owner; foreign keys bind it to known seats and reservations. Allocation starts BEGIN IMMEDIATE, checks the whole selection, writes the reservation and every claim, and commits before success is returned. Conflicts and SQL failures roll back the entire operation. Reads use one transaction for a consistent view.

MOVIE_SEATS_DB selects the persistent file, defaulting to instance/movie-seats.sqlite3. Startup creates a new version-1 database transactionally, reuses a recognized database, and refuses unrecognized or newer schemas. It never resets an existing database to make startup succeed. This checkpoint introduces no migration of historical development data.

Finish bookings and recover replies

Terminal states · safe retries

The request

Recorded prompt · unchanged from the build guide

Movie Seats can now hold seats and return a reservation ID. I’d like a
client to be able to use that ID to confirm the booking or cancel the hold
so someone else can book the seats. This should work for holds made with
the first version too.

A client can lose the reply to a request. I’d like it to be able to retry
safely, even after the service restarts. If the lost reply was for the
original hold, the caller should be able to find out whether its seats were
held and recover the reservation ID. It should also be safe to repeat a
confirmation or cancellation.

Give me a design proposal [use $ca-design-proposal].

The design proposal

Recorded assistant response

A booking client needs to finish or release its held seats and recover a lost reply without creating another reservation or changing an already completed outcome.

Milestone 2 — comparison baseline. Fresh implementation edaddef provides atomic holds, durable ID lookup, and 33 passing tests. Its Store.hold creates a new reservation for every successful unkeyed call, and every reservation remains held. Its immutable requested-seat rows and separate active claims provide the basis for safe completion and replay.

Domain — Intentions and Required capabilities. The caller wants to keep its group booked by confirming, release the group by cancelling, and recover creation when its reply is lost. The service will add confirmation and cancellation by ID, plus durable creation identity through a caller-generated request_key supplied before sending the request.

Rules — identity and completion. A key names one seat selection for this service. Canonical seat order makes A3+A4 and A4+A3 equivalent. Reusing the key for A2+A3 returns 409, even if those seats are available. Only successful creation consumes a key; failed validation or an unavailable group leaves the key reusable. Keys remain bound after cancellation or confirmation. Replaying a cancelled reservation returns that cancelled reservation and cannot acquire the seats again.

Current reservationConfirmCancel
heldconfirmed; keep every claimcancelled; release every claim
confirmedReturn the same confirmed booking409; preserve the booking
cancelled409; preserve cancellationReturn the same cancelled reservation

This terminal-state policy protects a completed result from a delayed conflicting request. Cancellation remains a hold operation, rather than a way to undo a confirmed booking.

Compatibility choice. Requiring a key would make an existing request such as {"seats":["A3","A4"]} fail with 422. I propose keeping the key optional: that request retains milestone-1 behavior, while {"seats":["A3","A4"],"request_key":"party-17"} gains replay recovery. Existing holds can complete after upgrade but cannot retroactively gain a lost creation key. No ambiguity prevents proceeding under this compatibility policy.

Architecture — participants and transactions. The booking client owns key generation and retention. The API validates request shape and translates results. The reservation service owns equivalence and lifecycle decisions. SQLite stores the key-to-reservation association and serializes competing creation or completion operations. Multiple workers continue to coordinate through the same local file.

Subsystem Design — Components. Within movie_seats, these changes extend the fresh implementation:

Package or moduleComponents: existing → proposed responsibility
domain.py — changedSelection rules → also validate keys, define terminal transitions, and represent creation versus replay with a Creation result.
db.py — changedAllocate and look up holds → first resolve a key, compare its original selection, perform completion, and migrate version 1 to 2.
api.py — changedCreation and lookup → accept an optional key, distinguish 201 creation from 200 replay, and expose confirm/cancel.
tests/fixtures/release_v1.sql — newFreeze a database generated by this run’s milestone-1 code, providing an independent upgrade input.
scripts/acceptance.py — changedHold/restart rehearsal → also upgrade a previous hold and rehearse lost-reply recovery and repeated completion over HTTP.

Subsystem Interfaces — Interfaces and Exchanges. POST /reservations adds optional request_key: 1–128 ASCII characters matching [A-Za-z0-9][A-Za-z0-9._:-]*. Omitted or null means unkeyed creation. First success returns 201; an equivalent keyed replay returns 200 with the same ID and current state. Returning current state lets a caller discover that another action already confirmed or cancelled the reservation.

POST /reservations/{id}/confirm and /cancel need no body and return 200 on success or repetition. Unknown IDs return 404; incompatible terminal operations and key reuse return distinct 409 error codes. Existing invalid-request and database-busy contracts remain. Screening reports confirmed seats as unavailable; cancelled reservations remain retrievable with their original seats.

State Management — State elements and migration. Version 2 adds a requests table mapping a unique key to one reservation ID. A creation transaction checks this mapping before checking availability, so the caller’s own hold cannot make its retry fail. Key insertion, reservation creation, and all seat claims commit together. Original selections remain immutable and support equivalence checks after claims are released.

Completion reads state under BEGIN IMMEDIATE. Confirmation updates status while retaining claims. Cancellation updates status and deletes claims for that reservation ID in the same transaction. Repeated cancellation performs no deletion, preventing it from releasing seats subsequently acquired by someone else. Concurrent confirm/cancel requests produce one terminal winner and one conflict.

Migration adds the table without rebuilding or replacing existing reservations, advances user_version only in the same successful transaction, and is safe to reopen. Unknown newer versions remain rejected. A migration failure preserves the prior database.

Verification — Tests. Proposed additions cover the complete transition matrix; key validation and reordered selection; mismatch rejection; replay after restart, confirmation, and cancellation; failed requests not consuming keys; same-key contention; concurrent confirm/cancel; and cancellation after reallocation. Real SQLite migration checks use the frozen fresh version-1 fixture and verify unchanged IDs, requested seats, and claims. Existing atomicity and HTTP checks remain.

This simulates a lost reply; it does not claim a network-fault injection. The milestone-1 scenario will also run against the evolved service.

Milestone 03

Release abandoned holds

Absolute deadlines · container recovery

94 tests passed0e994e4Markdown recording ↗

The request

Recorded prompt · unchanged from the build guide

Movie Seats now lets clients confirm or cancel a hold. I’d like each new
hold to have a time limit, and I’d like the service to tell the caller when
the hold expires. Once an unconfirmed hold expires, its seats should be
available for booking again. Confirmed bookings should keep their seats.

When we stop the service for maintenance or an upgrade, that downtime
should count toward the hold time. If a deadline passes while the service
is stopped, the seats should be available when it starts accepting requests
again.

Upgrading should preserve reservations made with earlier versions. I’d also
like to run the service in a container and keep those reservations when we
replace the container.

Give me a design proposal [use $ca-design-proposal].

The design proposal

Recorded assistant response

Booking clients need abandoned holds to release their seats on time, while operators need those deadlines and confirmed bookings to survive downtime, upgrades, and container replacement.

Milestone 3 — comparison baseline. Fresh implementation 9af1797 has durable holds, confirmation, cancellation, keyed recovery, version-2 migration, and 66 passing tests. Its stored reservations have no deadline. Store.get and screening read without changing state, and complete can confirm any held reservation regardless of elapsed time. No container packaging exists.

Domain — Intentions and Required capabilities. A caller needs a definite deadline and eventual release of an abandoned group. A confirmed booking must retain its seats. The operator needs service downtime to count and upgrades to preserve existing reservation identity and retry mappings. This adds expiration and persistent container deployment to the current service.

Rules — the timing boundary. Every new hold receives an absolute deadline. At now >= deadline, an unconfirmed hold becomes expired and releases all claims. Confirmation and cancellation of an expired hold return 409 reservation_expired; neither reopens it or changes the recorded reason. Keyed replay returns 200 with the original ID, deadline, and current expired state. A new booking requires a new key. Confirmation completed before expiry remains final, even after its former deadline.

Eligibility is decided after acquiring the SQLite write lock. For a deadline of 12:00:05.000000, a confirmation arriving at 12:00:04.900000 but obtaining the lock at 12:00:05.000000 is too late. An arrival-time policy would accept it despite the elapsed deadline; I recommend transaction-time eligibility so competing workers agree on one serialized decision. Tests will cover the microsecond before, exact equality, and a request delayed behind a real lock.

Upgrade choice. Earlier holds have no original timestamp from which to reconstruct a deadline. Expiring them immediately would release A3+A4 as soon as the upgrade runs; leaving them indefinite would preserve abandoned holds forever. I propose a one-time grace deadline of migration time plus the configured duration. IDs, selections, claims, and keys survive. Previously confirmed or cancelled records keep their state and a null deadline. Reopening the database or changing duration never renews an assigned deadline.

Architecture — participants and runtime. The reservation service uses the host’s UTC clock and SQLite file; it does not rely on an in-memory countdown or background scheduler. Startup and every valid booking operation clean up due holds before returning state or allocating seats. Therefore a service that was stopped past a deadline exposes released seats when it becomes ready. An idle database may retain an unswept row until the next operation, but the API never relies on that stale row without applying the deadline.

This simple design acquires the write lock for booking reads as well as writes. That trades read concurrency for one clear ordering of expiry, confirmation and allocation in this small twelve-seat example. Accurate host wall time is an operating assumption; clock jumps can change when an unseen deadline is reached. Once a reservation is persisted as expired, a backward clock adjustment does not revive it.

Subsystem Design — Components. Within movie_seats, the changes are:

Package or moduleComponents: existing → proposed responsibility
clock.py — newNo time abstraction → UTC integer microseconds and exact response formatting, with an injectable clock for tests.
db.py — changedState-only operations → common expiry-aware transaction, one-time deadlines, persisted expiration, and version-3 migration.
domain.py — changedThree-state completion policy → add terminal expired rejection while retaining confirmed/cancelled rules.
app.py — changedDatabase-path configuration → also validate hold duration and initialize/migrate/expire before accepting requests.
Dockerfile, compose.yaml, .dockerignore — newHost-only execution → locked runtime, nonroot service, localhost port, and a named data volume.
Tests and acceptance scripts — changed/newCompletion/retry checks → deterministic timing, upgrades from this run’s frozen v1/v2 data, process downtime and actual container replacement.

Subsystem Interfaces — Exchanges and controls. Reservation responses add expires_at, an ISO 8601 UTC timestamp with microseconds, or null for legacy terminal records. Existing endpoints and request-key rules remain. MOVIE_SEATS_HOLD_SECONDS selects an integer from 1 to 86400, default 300; invalid values stop startup clearly. The setting affects new holds and the first upgrade grace period, never existing deadlines.

docker compose up --build runs the service with its SQLite file under /data on a named volume. The image will use the repository’s Python version, a pinned uv version, and uv sync --locked --no-dev. The existing host Uvicorn workflow remains supported. Replacing the container preserves the volume; deleting that volume intentionally deletes its database.

State Management — atomic effects and failure. Version 3 adds integer expires_at_us and a due-hold index. Within BEGIN IMMEDIATE, the service samples time once and atomically changes due held rows to expired while deleting only their claims. It then creates a savepoint for the requested action. A domain rejection rolls back action work but commits due cleanup; thus a rejected late confirmation still leaves a durable expired record. SQL or infrastructure failures roll back the entire transaction. IDs, requested selections, and request mappings are retained throughout.

Verification — Tests. Deterministic tests will check deadline equality, no renewal on replay/restart/configuration change, retained confirmed claims, persisted expiry after rejected work, rollback on failed release, and lock-wait ordering. Frozen databases from the two fresh implementation commits will verify migration, grace assignment, terminal-state preservation and failure rollback. Existing tests and the earlier process scenarios remain part of regression verification.

Run uv run --locked python -m pytest -q and uv run --locked python scripts/acceptance.py --milestone 3. Docker Desktop is available for that check.
